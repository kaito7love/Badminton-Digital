# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Badminton Digital Management — full-stack court booking/management system. React SPA frontend, Node/Express REST API backend, MySQL via Sequelize. Repo layout: `frontend/`, `backend/`, `docs/` (SRS, architecture, API design), `postman/`, `k6/` (load testing), `docker/` (compose + Dockerfiles).

## Commands

### Backend (`backend/`)
```bash
npm install
npm run dev        # nodemon dev server, http://localhost:5000
npm start           # production start
npm test            # Jest unit tests (backend/tests/)
npm test -- courtService.test.js   # single test file
npm run migrate     # sequelize-cli db:migrate (also creates the admin/employee/customer/branch_manager roles)
npm run seed         # sequelize-cli db:seed:all — demo data with public passwords; refuses under NODE_ENV=production unless ALLOW_DEMO_SEED=true
npm run create-admin # first admin for a real install, from ADMIN_EMAIL / ADMIN_PASSWORD (>= 12 chars) / ADMIN_FULL_NAME env vars
```
Requires MySQL >= 8.0 and a `.env` (copy from `.env.example`) with `DB_*`, `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` — two different random strings of 32+ chars; the server refuses to boot on the old placeholder values or identical secrets.

### Frontend (`frontend/`)
```bash
npm install
npm run dev       # Vite dev server, http://localhost:5173, proxies /api -> localhost:5000
npm run build
npm run preview
npm test           # Vitest
```
`.env` needs `VITE_API_BASE_URL` (must be prefixed `VITE_` to be exposed via `import.meta.env`).

### Full stack via Docker
```bash
cp docker/.env.example docker/.env   # DB_PASSWORD, DB_ROOT_PASSWORD (compose refuses to start without them)
cd docker && docker compose up --build   # http://127.0.0.1:8080; backend waits for DB, migrates, then starts
```
The public portfolio demo is deployed differently — one Render web service built from `docker/app.Dockerfile` (backend also serves the frontend build, same origin) + Aiven MySQL over TLS, reset nightly by `.github/workflows/demo-reset.yml` (`backend/scripts/demo-reset.js`: drop all tables → migrate → seed). Step-by-step in `docs/DeploymentGuide.md` §4; blueprint in `render.yaml`.

## Architecture

### Backend layering
Standard layered Express app: `routes/` → `controllers/` → `services/` (business logic) → `models/` (Sequelize). `validations/` holds express-validator rule sets applied at the route level. `middleware/authMiddleware.js` verifies the JWT and attaches `req.user` (with `role`, `employee`, `customer` eager-loaded); `roleMiddleware.js` gates by role name; `branchContextMiddleware.js` resolves the active branch/tenant context; `requestContextMiddleware.js` sets up per-request context (used for activity logging); `errorHandler.js` is the centralized error middleware registered last in `server.js`.

All models are wired up in `models/index.js`, which is the single source of truth for associations (not each model file) — check it before adding a new relation.

Roles: `admin` (full access, all branches, can switch active branch via `X-Branch-Id`), `branch_manager` (same operational scope as `admin` — courts, employees, reports, inventory — but locked to their own branch; added in migration `20260815300002-add-branch-manager-role.js` and already gated on most routes and frontend routes/nav, not just a DB stub), `employee` (day-to-day operations within their branch: courts, bookings, checkout, customers, inventory), `customer` (own bookings only, can self-register). Auth flow: `POST /api/v1/auth/login` takes an `identifier` (phone number or email) + password and issues a short-lived access token (15m) + refresh token (7d); `apiClient` on the frontend auto-refreshes on 401. Refresh tokens are stored as sha256 only.

Secrets and staff accounts: the `User` model's `defaultScope` excludes `passwordHash`/`refreshToken` (Sequelize applies it to includes too) — only `AuthService` loads them, via `User.scope('withSecrets')`. `errorHandler.js` must never return raw `err.errors`: Sequelize error items carry the whole record in `instance`, so it only emits `[{ field, message }]`. Editing/deleting staff accounts goes through `EmployeeService.assertCanManage` (branch_manager may touch only `employee` accounts; nobody deletes an admin or themselves), mirrored for the UI in `frontend/src/utils/roles.js#canManageStaff`.

Money flows: bank transfer is off unless `PAYMENT_BANK_ID`/`PAYMENT_BANK_ACCOUNT_NO`/`PAYMENT_BANK_ACCOUNT_NAME` and a 32+ char `PAYMENT_WEBHOOK_SECRET` are all set (`utils/paymentConfig.js`) — `generateVietQRUrl` returns null otherwise, and court checkout, POS and online orders reject `transfer` with 400. `POST /payments/webhook` is fail-closed (`middleware/paymentWebhookAuth.js`: 503 unconfigured, 401 bad secret) and requires an `amount` matching the payment; rejections are audited as `payment.webhook_rejected`. Court fees use interval overlap with the branch-local peak window (`priceCalculator.calculateCourtFee`), and a court transfer accrues the finished segment into `court_sessions.accrued_court_fee`/`billed_from` — anything that bills a session must go through `calculateSessionCourtFee`, never recompute from `startTime`. Manual discounts need a reason and are capped for `employee` by setting `discount_policy` (`utils/discountPolicy.js`). Open online transfer orders hold a voucher use (`VoucherService.countUsage`).

Customer data boundaries: only staff roles may send `X-Branch-Id` — `branchContextMiddleware` returns 403 for a customer token with the header and for a `branch_manager`/`employee` account without an employee row. Operational reads (`GET /courts`, `/accessories`, `/products`, `/product-categories`) are staff-only; customer pages use `/public/*`. `PUT /bookings/:id` is staff-only and accepts only `courtId`/`bookingDate`/`startTime`/`endTime`. Self-registration never attaches an existing walk-in customer profile with the same phone (the account gets its own profile, `phone` null if the number is taken); staff verify the customer and merge the walk-in history at the counter via `POST /customers/:id/merge-into-account` (`CustomerService.mergeIntoAccount`, audited as `customer.merged`).

HTTP/deploy config lives in pure, tested helpers: `utils/serverConfig.js` (`TRUST_PROXY_HOPS`, default 0 — compose sets 1 (nginx) and `render.yaml` sets 3, because on Render requests pass Cloudflare → Render's ingress → an internal load balancer; measured on the live demo, 1 or 2 yield a proxy IP; `CORS_ORIGIN`, which in production defaults to *no* cross-origin since both deploys are same-origin), `config/dbSsl.js` (`DB_SSL`/`DB_SSL_CA`, always verifies the server cert), `utils/frontendStatic.js` (only active when `FRONTEND_DIST_DIR` is set). `DEMO_MODE=true` (`utils/demoMode.js`) locks the demo accounts printed on the login page — password change/reset, staff phone edit/delete, and the demo customer's phone/email return 403 — so one visitor can't lock out the next; the list must match the seeders (a test checks). In production, seeding requires `DEMO_ADMIN_PASSWORD` (`utils/demoSeedGuard.js#resolveDemoAdminPassword`) because `Admin@123` is public in this repo.

### Competition service integration (plan 23)
`backend/src/integrations/competition/` is the only place the main app knows about `services/competition-service`. It is **off unless all five `COMPETITION_*` env vars are set** (`config.js`: none → `/api/v1/competition` answers 503 `COMPETITION_DISABLED`; some but not all, or a bad key/secret → the server refuses to boot). `gateway.js` (mounted in `server.js`) authenticates with the normal JWT (SSE routes accept `?token=` like `/realtime/stream`), runs `branchContextMiddleware`, then re-signs an ES256 service token per request (`serviceToken.js`; 60 s, 300 s for SSE) with scopes capped by role (`roleScopes.js` — never `ops:admin`) and `org` from the active branch (admin without `X-Branch-Id` → `*`; customers carry `player = bd:customer:<id>`). `routeMap.js` is an allowlist by resource prefix + method (`events`, `ops`, `…/ai` never reach the service); the service enforces per-route scopes itself. A 401 from the service becomes 502 `COMPETITION_AUTH_FAILED` on purpose — passing it through would make `apiClient` think the session expired. Events: `CustomerService` writes `bd.customer.updated|merged|deleted` rows to `integration_outbox` in the same transaction (even while the integration is off); `dispatcher.js` delivers them HMAC-signed with a per-subject order, backoff and a `dead` state. Raw SQL in the dispatcher must pass UTC strings, not `Date` objects (the driver formats `Date` in the Node process timezone — it caused instant retries). Inbound: `routes/competitionWebhookRoutes.js` (mounted *before* the global `express.json()` because it verifies the signature over the raw bytes; fail-closed 503/401, dedup in `integration_inbox`) turns finalized/unfinalized/cancelled tournaments and closed sessions into `ActivityLog` rows. Keys/secrets: `npm run competition:keys` (writes `backend/.keys/competition.env`, gitignored). Deploy (plan 24): the Render demo image (`docker/app.Dockerfile`) also contains `services/competition-service` and runs it in the **same container** (`docker/demo-entrypoint.sh`): only when `COMPETITION_DB_NAME` is set it runs `backend/scripts/competition-boot.js` (fresh in-RAM ES256 keypair each boot, derives both processes' env from the two Render-generated HMAC secrets), then a background loop that waits for the backend, migrates the second database and runs the service on 127.0.0.1:5100 (restarts after 5 s); the backend stays PID 1. Unset → the two secrets are unset too (the backend refuses partial config). `DB_SSL_CA` accepts PEM / `\n`-escaped PEM / base64 / file path in both apps. The nightly demo reset (`.github/workflows/demo-reset.yml`) resets the second DB *after* the main one (`services/competition-service/scripts/demo-reset.js`, skipped without the `COMPETITION_DB_NAME` secret). docker-compose: service `competition` sits behind `--profile competition`. Postman folder `24 · Competition` is skipped by `docs:build`.

### Public competition hub `/thi-dau` (plan 27)
A portfolio-style public area inside the same web app where customers follow the venue's tournaments / social sessions **without logging in** and register online (logged-in customer, automatic — no staff approval). Frontend: `frontend/src/features/competition/pages/hub/` + `components/public/` + `PublicShell` (own shell, no shop/staff menu), routes spliced into `competitionPublicRoutes`, `FeatureGate hub` when the feature is off, menu "Thi đấu ▾" in the shared header (`siteNav.js`). Pure logic in `lib/publicHub.js` and `lib/registerFlow.js` (Vitest); data via `api/publicApi.js`. Gateway: resource `public` in `routeMap.js` is GET-only and open to anonymous tokens (scopes `ranking:read public:read`), with its own limiter (900 req/min/IP — a whole venue shares one Wi-Fi IP) and `streamGuard.js` (40 public SSE streams/IP, 300 total); customer-only scope `entry:self` covers `POST/DELETE /me/tournaments/:id/entries`, `POST/DELETE /me/sessions/:id/signup`, `GET /me/partners`. The service decides what a viewer sees (`player/domain/profile.js#publicRef`): anonymous only gets `public` profiles (short name/nickname), logged-in gets full names except `hidden`, the record's owner/participants/staff see everything; masked people are `{ id: null, name: "Thành viên A3F2", masked: true }`, and public schemas are closed (`additionalProperties: false`) so a leak fails a test. Fixed-pair doubles register self + one partner in one call; a partner without an account becomes an `online_guest` profile (hidden, phone visible to staff only, max 5 new guests per user per 24 h, one phone = one profile) with a provisional quick-assess rating staff confirm at the counter. Players with no rating cannot register (`NEEDS_ASSESSMENT`) — the dialog sends them to self-assessment; the demo customer `0903333333` is unrated on purpose. Withdrawal is only possible before the draw (`WITHDRAW_LOCKED`). Social sessions have `maxPlayers` + `session_signups` (registered / waitlisted / attended / cancelled; capacity counts sign-ups ∪ present; waitlist promotion on cancel/leave/capacity increase; staff check-in turns a sign-up into `attended`). `tournament_entries.registered_via` (`staff` | `self`) lets staff see online registrations. The fee is a **display-only constant** (`FEE_PER_PERSON_VND = 200000`, "thanh toán tại quầy") — no online collection yet. `seed-demo.js` also seeds the hub (most profiles `public`, two tournaments open for online registration, an upcoming session with 8 sign-ups). Docs: `docs/05-extra/02-remediation/27-ke-hoach-trang-cong-khai-thi-dau.md`, service docs 02 §2.10/2.11, 06 §15–17, 07 §7.

### Multi-tenancy migration in progress
The system is mid-migration from a flat 13-table schema to a multi-branch (tenant) model — see `backend/docs/architecture/README.md`, `TARGET_SCHEMA.md`, and `MIGRATION_ROADMAP.md` (stages M1–M7). A `Branch` model and `branchId` foreign keys have been added across most entities (`Court`, `Booking`, `CourtSession`, `Employee`, `Invoice`, `Payment`, `ActivityLog`, and the newer inventory models `ExtraStock`/`StockMovement`/`GoodsReceipt`) — but deliberately *not* `Customer`: migration `20260815300001-unify-customers-chain-wide.js` dropped `branch_id` from `customers` so one customer identity (matched by phone) spans every branch in the chain, rather than being re-created per branch. `models/index.js` is still the source to check before trusting any relationship diagram elsewhere. Migrations for this effort live under `backend/src/migrations/` prefixed `m1`/`m2`/`m3` plus later dated ones; back up the DB before running them against real data.

### Core domain model
```
Branch ──< Court ──< Booking ──< CourtSession ──< SessionExtra >── Extra
                                          └── Invoice ── Payment
Role ──< User ──── Employee ──< ActivityLog
                └──── Customer
```
A `Booking` optionally becomes a `CourtSession` (the actual play session, opened/closed by staff); a session accrues `SessionExtra` (rented accessories) and settles into an `Invoice` + `Payment` at checkout.

### Frontend structure
Pages under `frontend/src/pages/<Feature>/` map roughly 1:1 to backend route groups (Courts, Bookings, Accessories, Customers, Employees, Reports, Settings). `contexts/AuthContext.jsx`, `contexts/ThemeContext.jsx`, and `contexts/BranchContext.jsx` (admin's active-branch switcher) are the global providers wrapping the router. `routes/ProtectedRoute.jsx` gates authenticated routes; `layouts/SidebarLayout.jsx` is the shared authenticated shell (desktop sidebar + mobile bottom nav). `services/apiClient.js` is the single Axios instance — it owns the auth header injection and the 401 → refresh-token → retry flow; new API calls should go through it rather than a fresh axios instance. Its exported `refreshAccessToken` only ends the session (clears storage, `authEvents` expired) when the server rejects the refresh (400/401/403); network errors/5xx just throw so callers retry — `AuthContext` likewise only logs out when `/auth/me` returns 401/403. `services/realtimeClient.js` (SSE) refreshes the token before every (re)connect, backs off 2→30 s, treats 60 s without the server's `ping` event (sent every 25 s by `realtimeController`) as a dead connection, and calls `onReconnect` so pages refetch. Dark mode is the default theme, toggled via a `dark` class on `<html>` (Tailwind `darkMode: 'class'`). The whole customer-facing side shares one header: `components/site/SiteHeader.jsx` (sticky 96 px bar on desktop, 80 px bar + a bottom tab bar below `lg`; Trang chủ ▾ · Đặt sân · Cửa hàng ▾ · Thi đấu ▾ with hover dropdowns, then theme toggle · cart · account menu; always-visible 5-tab bar on phones), used by `CustomerLayout`, `PublicShell` (`/thi-dau`, `/rankings`, `/players/:id`) and `HomePage` (`tone="dark"` + `overlay`: transparent over the hero, glass after scrolling, dark-only, no theme toggle). All of its menu data lives in the pure, tested `components/site/siteNav.js` (`buildSiteNav`, `resolveActive`) — add or move a menu entry there, never in a shell; `SiteHeader` also owns the shared scroll-to-top button and resets scroll to the top on page change (customer pages only, not for Back/Forward, `#anchors` or same-page `?filters`). The logo + wordmark are `components/brand/BrandLogo.jsx` (`BrandTile`, `BrandWordmark`, `BrandLogo`; 44 px tile, 24 px text, white tile in light mode; the racket glyph is `components/BrandMark.jsx`; the scroll-to-top button deliberately keeps its arrow). Pages inside these shells must ship both halves of every class (`text-slate-900 dark:text-white`, no bare `text-white` / `bg-slate-950`); the Kinetic skin's light palette is switched by `.kinetic-light` (`styles/kinetic.css`, whose surface uses `overflow-x: clip` — `hidden` would break the sticky header), which `CustomerLayout` puts on its root when the theme is light. `/dat-san` is a basic public booking page (the quick-booking widget is still on the home page, anchor `#booking-widget`); `/account` shows a rating card (`features/competition/components/MyRatingCard.jsx`, links to `/my-rating` or `/my-rating/assess`). Hard-coded sticky offsets under the header must stay ≥ the 97 px header (`lg:top-28`).

Competition UI (tournaments, social sessions, live scoring, TV boards, player ratings, rankings) lives entirely in `frontend/src/features/competition/` and talks only to the gateway `/api/v1/competition/*` through its own `api/competitionApi.js` (Idempotency-Key on writes, If-Match/ETag, Vietnamese error translation) layered on `apiClient`. `AppRoutes` only splices in `competitionStaffRoutes` / `competitionCustomerRoutes` / `competitionPublicRoutes`; `App.jsx` wraps `CompetitionProvider` (public `GET /competition/status` → menu hidden when the feature is off, "tạm ngưng" notice when the circuit breaker is open). Pure logic is in `lib/` (Vitest, no jsdom — components are covered by `react-dom/server` renders and by walking real Chrome); pages reload on the service's SSE `board` event but never while the user is mid-action (`useLiveResource.setBusy`). Details and per-slice results: `docs/05-extra/02-remediation/25-ke-hoach-giao-dien-thi-dau.md`.

### API convention
Base path `/api/v1`. Controllers return a consistent envelope: `{ success, data, message, errors }` (see `authMiddleware.js` for the shape used on auth failures — replicate it for new endpoints).
